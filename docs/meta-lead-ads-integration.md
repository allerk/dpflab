# Meta Lead Ads → DPFLAB CRM

This integration receives Meta Instant Form notifications, retrieves the full lead from Graph API v25.0 and inserts it into the same CRM pipeline as website leads.

## Runtime flow

1. Meta calls `GET /api/webhooks/meta-leads` once to verify the callback.
2. Meta sends a small Page `leadgen` notification to `POST /api/webhooks/meta-leads`.
3. The Worker verifies `X-Hub-Signature-256` over the exact request bytes with `META_APP_SECRET` before parsing JSON.
4. The Worker accepts only the configured Page and deduplicates repeated `leadgen_id` values in the delivery.
5. The Worker requests the full lead from `/{leadgen_id}` using Graph API v25.0, a Bearer token and `appsecret_proof`.
6. Standard fields and DPFLAB custom questions are normalized and passed to `ingestMetaLead(db, lead)`.
7. The repository must enforce uniqueness for the Meta external lead ID. Meta retries and partially repeated webhook batches must return the existing submission instead of creating another lead.

The endpoint only returns `200` after all relevant leads have been retrieved and persisted. A transient Graph or D1 failure returns a non-2xx response so Meta can retry. Some leads in a multi-lead delivery may already have been inserted; the database uniqueness constraint is therefore mandatory.

No request body, Graph response body, access token, lead ID or contact field is written to logs.

## Cloudflare configuration

Set the following as Worker secrets in both `develop` and `prod`:

```bash
npx wrangler secret put META_APP_SECRET --env develop
npx wrangler secret put META_LEADS_ACCESS_TOKEN --env develop
npx wrangler secret put META_LEADS_VERIFY_TOKEN --env develop

npx wrangler secret put META_APP_SECRET --env prod
npx wrangler secret put META_LEADS_ACCESS_TOKEN --env prod
npx wrangler secret put META_LEADS_VERIFY_TOKEN --env prod
```

- `META_APP_SECRET`: secret of the business-owned Meta app that owns the webhook subscription.
- `META_LEADS_ACCESS_TOKEN`: long-lived Page/system-user token with lead retrieval access, issued for the same Meta app as `META_APP_SECRET` so `appsecret_proof` validates. It is not the website Conversions API token.
- `META_LEADS_VERIFY_TOKEN`: a new random value generated by us and entered unchanged in the Meta Webhooks dashboard. It is not a Meta access token.

Add these non-secret Worker variables to each deployed environment:

```json
{
  "META_LEADS_PAGE_ID": "1205337539326627",
  "META_LEADS_FORM_LOCALES": "{\"1514307796630470\":\"ru\",\"27980848328265828\":\"ru\",\"1293909486000385\":\"et\",\"1395333806136980\":\"et\",\"1570981471069414\":\"en\",\"27487810977557355\":\"en\"}",
  "META_GRAPH_API_VERSION": "v25.0"
}
```

`META_LEADS_FORM_LOCALES` is optional, but without it a new Instant Form lead cannot reliably derive its language from Graph lead fields alone. Update the map whenever a form is duplicated or replaced.

The 2026-08-11 registration-number candidates are `27980848328265828` (RU), `1395333806136980` (ET) and `27487810977557355` (EN). Meta reports API-created forms as `ACTIVE` in the Forms Library; the `[DRAFT]` name is the review convention. They remain candidates until an owner explicitly attaches them to ads. Keep the earlier IDs in the locale map while old ads or organic form links may still generate leads.

The callback path must remain public at the Cloudflare Access layer. Protect `/admin`, not `/api/webhooks/meta-leads`. The application also bypasses edge caching for every `/api/webhooks/` GET so the verification URL and token are never cached.

## Meta dashboard setup

Use a Meta app owned by the DPFLAB business rather than a developer's unrelated business portfolio.

1. In the Meta App Dashboard, add **Webhooks** and select the **Page** object.
2. Set the callback URL to `https://dpflab.ee/api/webhooks/meta-leads` and enter the exact value stored as `META_LEADS_VERIFY_TOKEN`.
3. Subscribe the app to the Page `leadgen` field.
4. Subscribe the app to the DPFLAB Page through the Page `/{page-id}/subscribed_apps` edge with `subscribed_fields=leadgen`.
5. In Business Settings → Integrations → Leads Access, give the app/CRM and its system user access to DPFLAB leads.
6. Ensure the token has the current permissions Meta requires for lead retrieval, including `leads_retrieval` and the relevant Page permissions, and ensure Lead Ads Terms are accepted for the Page.
7. Put the app in the mode and complete any business verification/App Review required for production assets.
8. Use Meta's Lead Ads Testing Tool for each RU, ET and EN form. Confirm exactly one CRM record is created; resend the same delivery and confirm it is reported as a duplicate.

Do not place the App Secret or an access token in `wrangler.jsonc`, Git, a browser bundle, a webhook URL or logs.

Webhook ingestion is the real-time path, not a complete backup strategy. Add a scheduled reconciliation job later that reads recent leads from each known `/{form-id}/leads` edge and sends them through the same idempotent repository. That closes gaps caused by an expired token, an accidental app unsubscription or a Meta delivery incident without creating duplicates.

## Repository contract

The route calls:

```ts
ingestMetaLead(db, normalizedLead): Promise<{
  submissionId: number;
  inserted: boolean;
}>;
```

The data layer must:

- insert the lead into the ordinary CRM pipeline with origin `meta_instant`;
- atomically enforce uniqueness by provider/origin plus `externalLeadId` (the Meta `leadgen_id`);
- return `{ inserted: false }` and the existing submission ID for a retry;
- preserve `externalLeadId`, `formId`, campaign/ad set/ad IDs, locale, the five DPFLAB qualification answers, standard contact fields and the remaining custom fields;
- never overwrite employee-entered status, notes or financial values when a duplicate webhook arrives.

The normalized payload uses `idempotencyKey = meta:lead:<leadgen_id>` as an explicit cross-layer contract. Database uniqueness, rather than an in-memory cache, is the final authority.

## Downstream CRM events to Meta

Instant Form lifecycle feedback is a separate CRM Conversions API integration from the existing website CAPI. Meta explicitly notes that a web-events CAPI setup is not sufficient for Instant Form down-funnel data because the parameters and source are different.

For a lead that originated from a Meta Instant Form, the later CRM stage event should have this shape:

```json
{
  "event_name": "Schedule",
  "event_time": 1785240000,
  "event_id": "meta-lead-1514307796630470-booked",
  "action_source": "system_generated",
  "user_data": {
    "lead_id": "1514307796630470"
  },
  "custom_data": {
    "event_source": "crm"
  }
}
```

Use a deterministic `event_id` per lead and stage. Put the original Meta `leadgen_id` un-hashed in `user_data.lead_id`; Meta's current official SDK serializes `lead_id` without hashing and uses it specifically for Lead Ads matching. Email and phone, when also sent, must be normalized and SHA-256 hashed.

Use `action_source: "system_generated"` for a stage change generated by CRM workflow. Do not label an Instant Form lifecycle update as a website action. `event_source_url` is for website actions and is not required for `system_generated`.

DPFLAB can use a stable event mapping such as:

- qualified → `QualifiedLead` (or a stable custom name configured and tested in Events Manager);
- booked → `Schedule`;
- completed → `Purchase`, with positive `custom_data.value` and `custom_data.currency = "EUR"`.

Event names used for Conversion Leads optimization must be mapped and verified in Meta Events Manager/Test Events before campaign optimization is changed. `lead_id` is the strongest deterministic link to the original Instant Form lead; do not omit it merely because hashed phone/email are available.

Website-form leads remain a different case: the immediate browser/server Lead event belongs to the website interaction. Later admin-side CRM transitions are truthfully marked `system_generated` and use consented matching identifiers rather than pretending to carry a live browser request. They have no Meta Lead Ads `lead_id`.

The outbox sender is implemented but both lifecycle paths have explicit production gates. Set `META_CRM_EVENTS_ENABLED=true` for Instant Form feedback only after the owners confirm the applicable EU lawful basis/privacy wording and validate Test Events. Keep `META_SITE_CRM_EVENTS_ENABLED=false` until website-consent revocation is synchronized server-side. Until a gate is enabled, those rows remain retryable with `policy_not_enabled`.

Develop intentionally has no production `META_PIXEL_ID`. Use a separate Meta test dataset or Test Events configuration; never give staging the production Pixel plus a live CAPI token.
